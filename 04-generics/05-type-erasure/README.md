# Type erasure and restrictions

## 1. What it is

Generics exist **only at compile time**. The compiler checks your types, then **erases** them. Each type parameter is replaced by its first bound (or `Object`), casts are inserted where values come out, and the bytecode contains no `<String>` at all. This is **type erasure**.

At runtime, a `List<String>` and a `List<Integer>` are the same class, `ArrayList`. Almost every "you can't do that with generics" rule follows from this one fact.

## 2. Why it exists

Generics arrived in Java 5 (2004), when there were already millions of lines of code using plain `List` and `Map`. Erasure meant:
- Old code and new code could run together. A generic `List<String>` *is* a plain `List` at runtime, so it can be passed to a library written in 2002.
- The JVM didn't need to change. No new class per type argument, no extra memory per type.

The price: the JVM can't tell a `List<String>` from a `List<Integer>`, so anything that needs the type argument *at runtime* is restricted.

## 3. Core concepts

**Erasure of generic types.** `T` becomes its first bound, or `Object` if it has none:

```java
// What you write                          // What the JVM sees
class Node<T> {                            class Node {
    T data;                                    Object data;
    T get() { return data; }                   Object get() { return data; }
}                                          }

class Ranked<T extends Comparable<T>> {    class Ranked {
    T best;                                    Comparable best;
}                                          }
```

At each call site, the compiler adds the cast you'd otherwise write: `String s = node.get();` compiles to `String s = (String) node.get();`.

**Erasure of generic methods.** The same rule applies:

```java
static <T extends Shape> void draw(T shape)   // erases to  static void draw(Shape shape)
static <T> int count(List<T> items)           // erases to  static int count(List items)
```

**Bridge methods.** Erasure can break overriding, so the compiler patches it:

```java
class Node<T> {
    void setData(T data) { ... }         // erased: setData(Object)
}
class IntNode extends Node<Integer> {
    @Override
    void setData(Integer data) { ... }   // erased: setData(Integer). Not an override of setData(Object)!
}
```

To keep polymorphism working, the compiler adds a hidden **bridge method** to `IntNode`:

```java
void setData(Object data) {        // generated by the compiler
    setData((Integer) data);       // casts, then calls the real method
}
```

You'll mostly notice it through a stack trace. If raw types sneak a `String` in, the `ClassCastException` comes from the bridge's cast, in a method you never wrote.

**Reifiable vs non-reifiable types.** A type is **reifiable** if its full type information exists at runtime:

| Reifiable (fully known at runtime) | Non-reifiable (partly erased) |
|------------------------------------|-------------------------------|
| primitives: `int`, `double` | `List<String>`, `Map<String, Integer>` |
| non-generic types: `String`, `Order` | `List<? extends Number>` |
| raw types: `List` | type parameters: `T` |
| unbounded wildcards: `List<?>` | |
| arrays of these: `String[]`, `List<?>[]` | |

Only reifiable types can be used in `instanceof` and as array element types.

**Heap pollution.** This happens when a variable of a parameterized type points to an object that isn't of that type. It's caused by raw types and unchecked casts, and it shows up as a `ClassCastException` *later*, far from the cause:

```java
List<String> names = new ArrayList<>();
List raw = names;              // raw type: checks are off
raw.add(42);                   // "unchecked" warning, and heap pollution: an Integer in a List<String>
String first = names.get(0);   // ClassCastException, on a line that looks perfectly fine
```

**Generic varargs and `@SafeVarargs`.** A varargs parameter is an array. With a generic varargs `T... items`, the compiler must create a `T[]`, but `T` is erased, so it creates an `Object[]`. You get a warning at the declaration: "possible heap pollution".

```java
static <T> List<T> listOf(T... items) {          // warning: possible heap pollution
    return new ArrayList<>(Arrays.asList(items)); // only reads from the array: actually safe
}
```

If the method only **reads** the array (never stores into it, never returns or shares it), mark it `@SafeVarargs`. That removes the warnings at the declaration and at every call site:

```java
@SafeVarargs
static <T> List<T> listOf(T... items) { ... }
```

`@SafeVarargs` is allowed only on methods that can't be overridden (`static`, `final`, `private`) and on constructors. `@SuppressWarnings("unchecked")` is the weaker alternative: it hides the warning at the declaration but not at call sites.

### Restrictions

Every restriction comes from erasure, and each has a standard workaround:

| You can't... | Because | Instead |
|--------------|---------|---------|
| use primitives: `List<int>` | `T` erases to `Object`, and `int` isn't an object | wrapper types: `List<Integer>` |
| create an instance: `new T()` | at runtime there's no `T` to construct | pass a `Supplier<T>` (`Order::new`) or a `Class<T>` |
| declare `static T field` | a static field is shared by `Box<String>` and `Box<Integer>`: which `T` would it be? | make it non-static, or use a concrete type |
| check `obj instanceof List<String>` | the `<String>` doesn't exist at runtime | `obj instanceof List<?>`, then check the elements |
| cast `(List<String>) obj` safely | same reason: compiles with an "unchecked" warning, checks only `List` | check the elements, or keep the type through a `Class<T>` token |
| create a generic array: `new List<String>[10]`, `new T[10]` | arrays check their element type at runtime, and that type is erased | `List<List<String>>`; or `Array.newInstance(type, n)` with a `Class<T>` |
| make a generic exception: `class Failure<T> extends Exception` | `catch` matches at runtime, where `Failure<String>` and `Failure<Integer>` look the same | put the data in a field of a non-generic exception |
| `catch (T e)` | same reason | catch the bound, e.g. `catch (Exception e)`. Note that `throws T` **is** allowed |
| overload `print(List<String>)` and `print(List<Integer>)` | both erase to `print(List)`: same signature | give them different names: `printNames`, `printIds` |

```java
static <T> T create() {
    return new T();                               // compile error
}
static <T> T create(Supplier<T> factory) {
    return factory.get();                         // right: create(Order::new)
}

static <T> T[] newArray(Class<T> type, int size) {
    return (T[]) Array.newInstance(type, size);   // right: a real String[] when type is String.class
}
```

## 4. How it works under the hood

You can see erasure with `javap`, the class-file disassembler that comes with the JDK:

```
javac Box.java
javap -c Box.class     ->   public java.lang.Object get();
                            ...
javap -p IntNode.class ->   void setData(java.lang.Integer);
                            void setData(java.lang.Object);    <- the bridge method
```

Not *everything* is erased. The **declarations** keep their generic signatures in the class file, so reflection can read them. `Field.getGenericType()` on a `List<String> names` field returns `List<String>`. Frameworks like Jackson and Spring use this ("type tokens") to work out types at runtime. What's erased is the type argument of each *object*: an `ArrayList` instance never knows it was created as an `ArrayList<String>`.

## 5. Common mistakes and gotchas

**Trusting an unchecked cast.** A cast to a type parameter does nothing at runtime, so it can't fail where you'd expect:

```java
@SuppressWarnings("unchecked")
<T> T get(String key) {
    return (T) values.get(key);         // wrong: erased to (Object), always "succeeds"
}
Integer port = config.get("host");      // ClassCastException here, in the caller, not in get()

<T> T get(String key, Class<T> type) {
    return type.cast(values.get(key));  // right: a real check, with a clear message, inside get()
}
```

**Returning a generic varargs array.** The array is an `Object[]` when called from generic code:

```java
static <T> T[] arrayOf(T... items) { return items; }       // wrong: leaks the array
static <T> T[] firstTwo(T a, T b, T c) { return arrayOf(a, b); }  // creates an Object[]
String[] pair = firstTwo("x", "y", "z");                    // ClassCastException

static <T> List<T> firstTwo(T a, T b, T c) { return List.of(a, b); }   // right: use a List
```

**Putting `@SafeVarargs` on a method that isn't safe.** The annotation is a promise you make. The compiler doesn't check it. If the method stores into the array or returns it, the warning was telling you the truth.

**Expecting `getClass()` to know the type argument.**

```java
new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()   // true
```

**Overloads that only differ in type arguments.**

```java
void save(List<Order> orders) { ... }
void save(List<Customer> customers) { ... }   // compile error: name clash, same erasure
```

## 6. When to use / when not to

You don't choose to "use" erasure, but you work with it in these situations:
- **You need a type at runtime** (to create objects, arrays, or check instances): pass a `Class<T>` or a `Supplier<T>` explicitly.
- **You see an "unchecked" warning**: don't suppress it by reflex. Each one is a place where heap pollution can start. Suppress it only after you've proved the cast is safe, on the smallest scope, with a comment explaining why.
- **You write a generic varargs method**: add `@SafeVarargs` only if the method just reads the array. Otherwise take a `List<T>` instead.
- **You need a generic array**: prefer a `List<T>`. If you really need an array (e.g. inside a data structure), keep the `Object[]` private and never return it as a `T[]`.

## 7. Interview angle

1. **What is type erasure?** The compiler checks generic types, then removes them. Type parameters become their first bound (or `Object`), and casts are inserted at call sites. At runtime, `List<String>` and `List<Integer>` are the same class.
2. **Why did Java choose erasure?** Backward compatibility. Generic code had to run with existing pre-Java-5 libraries and JVMs, so a `List<String>` had to be a plain `List` at runtime.
3. **What is a bridge method?** A synthetic method the compiler generates in a subclass of a generic type, so overriding still works after erasure. `IntNode.setData(Integer)` gets a bridge `setData(Object)` that casts and delegates.
4. **Why can't you create a generic array, e.g. `new T[10]` or `new List<String>[10]`?** Arrays check every store at runtime (`ArrayStoreException`), using their element type. With erasure the element type would be wrong, so the check could pass when it shouldn't. Use a `List`, or `Array.newInstance` with a `Class<T>`.
5. **What is heap pollution, and what does `@SafeVarargs` do?** Heap pollution is a parameterized variable that points to an object of the wrong type, usually via raw types, unchecked casts or generic varargs. `@SafeVarargs` is the method author's promise that a generic varargs method doesn't misuse its array, and it silences the warnings.
6. **Can you overload `m(List<String>)` and `m(List<Integer>)`?** No. Both erase to `m(List)`, so the compiler reports a name clash.

## 9. Extra: casts the compiler can prove safe

Source: https://dev.java/learn/language/fp/generics/restrictions

Added from the dev.java "Restrictions on Generics" page. Section 3's table says a cast to a parameterized type gives an "unchecked" warning. That's true when the compiler **can't** prove the cast is right. When it can, the cast is allowed with **no warning**:

```java
List<String> list = new ArrayList<>();
Collection<String> coll = list;
Object obj = list;
List<?> wild = list;

ArrayList<String> a = (ArrayList<String>) list;   // no warning: only the class part changes, <String> is already known
List<String> b = (List<String>) coll;             // no warning: same reason
List<?> c = (List<?>) obj;                        // no warning: unbounded wildcard, nothing to check

List<String> d = (List<String>) obj;              // unchecked warning: from Object, <String> can't be checked
List<String> e = (List<String>) wild;             // unchecked warning: List<?> could be a List<Integer>
```

The rule of thumb: if the **type argument stays the same** (or the target is `<?>`), the runtime check on the class part (`ArrayList`, `List`) is all that's needed, so the cast is fully checked. If the cast would have to **invent** a type argument, the runtime can't verify it, and you get the warning.

Example: `examples/Example3_ProvablySafeCasts.java`.
